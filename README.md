# Домовед

**Домовед** — проект для связи жителей многоквартирного дома с управляющей компанией. Житель пользуется ботом и мини-приложением в MAX: привязывает квартиру, сообщает о проблеме, прикладывает фотографии и следит за решением. Сотрудник УК работает в отдельном кабинете: видит обращения своих домов, меняет статусы и уточняет детали у автора.

Проект команды **«Облачный Код»**, созданный для хакатона. Часть сценариев демонстрационная; границы работающих функций перечислены [ниже](#что-пока-демонстрационное).

## Что умеет проект

| Сценарий | Возможности |
| --- | --- |
| Первый вход | Бот и мини-приложение показывают приветствие и общую форму привязки квартиры. ФИО можно исправить; УК, дом и квартиру выбирают из каталога. В тестовом режиме заявка принимается автоматически. |
| Несколько квартир | Один житель может привязать несколько квартир; одну квартиру могут привязать несколько членов семьи. Привязки видны в боте и мини-приложении. |
| Обращения | Создание через бот или мини-приложение, до 10 фотографий, список, карточка, история и статусы «Новое», «В работе», «Решено». Текст обращения из бота разбирает модель Yandex Cloud: предлагает заголовок, категорию и приоритет. |
| Кабинет УК | Вход сотрудника по логину и паролю, доступ к назначенным домам, таблица обращений, фотографии, смена статуса, отклонение обращений с указанием причины, переписка с автором и управление контактами УК. УК может принимать и отклонять заявки на привязку квартиры, а для принятой заявки — удалять аккаунт жителя вместе с его обращениями. Изменения статуса, причины отклонения обращений и сообщения сотрудника доставляются жителю через бота. |
| Жизнь дома | План подъездов, этажей и квартир; сообщения между квартирами; квитанции и показания счётчиков; кадры камер; работы по дому; показатель «здоровья» по обращениям. |

## Как части связаны

```text
Житель в MAX ──┬──> chatbot/ ───────────┐
               └──> mini-app/ ──HTTP──> backend/ ──┐
                                                     ├──> PostgreSQL
Сотрудник УК ──────────────> /staff/ ──HTTP─────────┘
                         фотографии ──> общее файловое хранилище

app/ — общие модели БД и сервисы для бота и API
```

| Путь | За что отвечает |
| --- | --- |
| [`chatbot/`](chatbot/) | MAX polling, обработчики команд и кнопок, регистрация и обращения, фоновые уведомления. |
| [`mini-app/`](mini-app/) | Интерфейс жителя на Next.js, React и TypeScript. Маршруты в `app/`, экраны в `src/`. |
| [`backend/smart_city_api/`](backend/smart_city_api/) | FastAPI: вход, данные жителя, регистрация, обращения, сообщения, услуги и API сотрудника. |
| [`backend/smart_city_api/staff_web/`](backend/smart_city_api/staff_web/) | Интерфейс кабинета УК, который FastAPI отдаёт по `/staff/`. |
| [`app/database/`](app/database/) | Общие модели SQLAlchemy, сессии и функции работы с данными. |
| [`app/services/`](app/services/) и [`app/ai/`](app/ai/) | Логика регистрации и обращений, интеграция с моделью Yandex Cloud. |
| [`backend/migrations/`](backend/migrations/) | Миграции Alembic: схема БД обновляется перед запуском сервисов. |
| [`backend/evaluation/openapi.yaml`](backend/evaluation/openapi.yaml), [`backend/evaluation/openapi.json`](backend/evaluation/openapi.json) | OpenAPI 3.1 публичного API: методы, параметры и форматы ответа. Снимок получен с сервера для проверки. |
| [`backend/openapi.yaml`](backend/openapi.yaml), [`backend/openapi.json`](backend/openapi.json) | Контракт локального кода backend; обновляется экспортом из приложения. |
| [`backend/DATA-API.yaml`](backend/DATA-API.yaml) | Версия конфигурации, команда, HTTPS-адрес API и обязательные проверки с параметрами, ролями и ожидаемыми ответами. |
| [`backend/test-data.json`](backend/test-data.json) | Синтетические данные и тела запросов для воспроизводимой проверки. |
| [`backend/test-accounts.example.json`](backend/test-accounts.example.json) | Роли и порядок предоставления тестовых доступов; реальные пароли и данные запуска MAX передаются отдельно. |
| [`compose.yaml`](compose.yaml), [`compose.local.yaml`](compose.local.yaml), [`compose.production.yaml`](compose.production.yaml) | Контейнеры проекта и настройки локального и серверного запуска. |

Все интерфейсы используют одну PostgreSQL. Связь «житель ↔ квартира» хранится отдельно от квартиры: это позволяет нескольким людям жить в одной квартире и одному человеку иметь несколько квартир. Фотографии лежат в общем файловом томе; в БД сохраняются ссылки на файлы. Схему меняют миграции Alembic, поэтому удалять базу при изменении моделей не нужно.

## Материалы для проверки API

Команда — **«Облачный Код»**, решение — **«Домовед»**. Базовый адрес проверяемого API: **[https://201.34.159.33/api/v1](https://201.34.159.33/api/v1)**. К нему добавляется относительный путь метода, например `/me`; отдельного метода `GET /api/v1` нет. [Swagger](https://201.34.159.33/api/docs) доступен по отдельному адресу.

| Требование | Материал |
| --- | --- |
| Описание методов и форматов OpenAPI 3.1 | [openapi.yaml](backend/evaluation/openapi.yaml) и [openapi.json](backend/evaluation/openapi.json); снимок публичного API от 30 сентября 2026 года |
| Конфигурация проверки | [DATA-API.yaml](backend/DATA-API.yaml): версия, команда, HTTPS-адрес, 26 проверок, HTTP-методы и пути, параметры, роли, статус-коды и JSON Schema ответа |
| Версия формата конфигурации | `1.0`, собственная [DATA-API.schema.json](backend/DATA-API.schema.json); шаблон организаторов не предоставлен |
| Воспроизводимые тестовые данные | [test-data.json](backend/test-data.json); автоматический прогон создаёт отдельную временную базу |
| Тестовые доступы | [test-accounts.example.json](backend/test-accounts.example.json): требуются житель MAX и сотрудник УК; реальные доступы необходимо подготовить и передать проверяющему отдельно |

Синтетические ID из JSON относятся только к временной тестовой базе. Для проверки публичного сервера подставляют ID выделенного тестового дома, квартир и счётчика, свежую `initData` MAX, учётные данные сотрудника и текущий открытый период показаний. POST-проверки изменяют тестовые данные; административный доступ не требуется. Проверки состояния API доступны по [health/live](https://201.34.159.33/health/live) и [health/ready](https://201.34.159.33/health/ready), вне `/api/v1`.

Контракт и все запросы DATA-API проверяются тестами backend. Порядок экспорта и запуска описан в [backend/README.md](backend/README.md#материалы-проверки-api). Перед проверкой нужно обеспечить работу сервера и действующий HTTPS-сертификат на весь период проверки.

Публичный API и локальное приложение используют одинаковый контракт OpenAPI. Проверки сотрудника в DATA-API используют `POST /staff/auth/login`, cookie-сессию и CSRF из `GET /staff/me`. Для API-клиентов также доступен `POST /staff/auth/token`, выдающий токен сессии для заголовка `Authorization: Bearer`. После изменения серверной версии нужно обновить оба экспорта OpenAPI и сверить DATA-API. Проверенный сертификат HTTPS истекает **5 октября 2026 года в 11:13:11 UTC**; для более поздней проверки требуется его продление.

## Быстрый локальный запуск на Windows

Понадобятся Docker Desktop с Linux-контейнерами, Docker Compose v2 и доступ к загрузке образов. При запуске бота также нужны токен MAX и доступ к Yandex Cloud. Команды выполняйте **из корня репозитория** в PowerShell.

1. Скопируйте шаблон настроек:

   ```powershell
   Copy-Item .env.docker.example .env.docker
   ```

2. В `.env.docker` замените `POSTGRES_PASSWORD` и `LOCAL_SESSION_SECRET` двумя разными случайными значениями. Для пароля БД здесь проще использовать латинские буквы, цифры, `_` и `-`. Файл с настоящими секретами исключён из Git.

3. Запустите мини-приложение, API и PostgreSQL:

   ```powershell
   docker compose --env-file .env.docker -f compose.yaml -f compose.local.yaml up -d --build
   ```

4. Откройте [мини-приложение](http://localhost:3000) и выберите локальный вход. Compose применит миграции и создаст тестового жителя с квартирой.

| Адрес | Что откроется |
| --- | --- |
| `http://localhost:3000` | Мини-приложение жителя |
| `http://localhost:8000/staff/` | Кабинет сотрудника УК |
| `http://localhost:8000/api/docs` | Swagger API |
| `http://localhost:8000/health/ready` | Проверка API и БД |
| [https://201.34.159.33/api/v1](https://201.34.159.33/api/v1) | Базовый HTTPS-адрес проверяемого API |
| [https://201.34.159.33/api/docs](https://201.34.159.33/api/docs) | Публичный Swagger для выполнения запросов |

Чтобы добавить бота, заполните `BOT_TOKEN`, `YANDEX_API_KEY`, `YANDEX_FOLDER_ID` и, если нужно, `MINI_APP_BOT_USERNAME` в `.env.docker`, затем запустите:

```powershell
docker compose --env-file .env.docker -f compose.yaml -f compose.local.yaml --profile bot up -d --build
```

Бот получает события через polling. С одним токеном должен работать только один экземпляр; активная webhook-подписка также мешает polling. Если бот уже работает на сервере, не запускайте локальную копию с тем же токеном.

### Регистрация и демонстрационные дома

В Compose по умолчанию включён `ONBOARDING_TEST_MODE=true`. При старте создаётся демонстрационная УК «Домовед» и пять домов в Казани на улице Солнечной. Пользователь проверяет или меняет ФИО, выбирает УК, дом и существующий номер квартиры. Заявка сразу получает статус «Принята», квартира становится доступна и в боте, и в мини-приложении. Повторное добавление той же квартиры не создаёт второй привязки.

Чтобы проверить ручное рассмотрение, задайте `ONBOARDING_TEST_MODE=false` в `.env.docker` и пересоздайте сервисы. Тогда заявка появится в разделе «Заявки» кабинета УК; сотрудник сможет принять или отклонить её. Отключение тестового режима не удаляет уже созданные дома и привязки.

Локальный житель из `seed_local` уже имеет квартиру — это быстрый способ посмотреть основной интерфейс. Полный экран первого входа удобнее проверять через нового пользователя MAX.

### Сотрудник УК

Аккаунты сотрудников создаются отдельно: аккаунт жителя не даёт вход в кабинет. Сначала посмотрите ID домов:

```powershell
docker compose --env-file .env.docker -f compose.yaml -f compose.local.yaml exec api python -m scripts.manage_staff list
```

Затем создайте сотрудника и назначьте дома, повторив `--house` для каждого ID:

```powershell
docker compose --env-file .env.docker -f compose.yaml -f compose.local.yaml exec api python -m scripts.manage_staff create manager --name "Сотрудник УК" --house 1 --house 2
```

Команда спросит пароль дважды в терминале; минимум 12 символов. Откройте `/staff/` и войдите под созданным логином. Для существующего сотрудника команда `assign` **заменяет** список домов целиком: перечислите все дома, к которым нужно оставить доступ. Новые демонстрационные дома не назначаются сотруднику автоматически.

## Основные сценарии

**Житель.** Открывает бота или мини-приложение из MAX, проходит общую регистрацию, выбирает квартиру и дом. Обращение можно составить в чате с фото или в форме мини-приложения с местом на плане и вложениями. После отправки запись видна в списке и кабинете УК. Для обращений из бота нужны ключи Yandex Cloud и доступ к модели.

**Сотрудник.** Видит только назначенные ему дома. В «Обращениях» открывает описание, фото и диалог, переводит заявку в работу или завершает её. Бот отправляет автору уведомление о смене статуса или сообщение сотрудника. В «Заявках» видны попытки привязки квартир; при включённом тестовом режиме они уже приняты. В «Контактах» можно указать телефон, почту, адрес приёмной и сайт для конкретного дома.

**Рассмотрение заявок и удаление аккаунта.**

- В «Обращениях» сотрудник УК может отклонить обращение, указав причину. Оно исчезает из списков обращений, а автор получает уведомление с причиной в MAX; запись сохраняется в БД.
- В «Заявках» УК может принять или отклонить ожидающую заявку на привязку квартиры. В тестовом режиме такие заявки принимаются автоматически.
- Для принятой заявки доступна кнопка «Удалить пользователя»: после подтверждения удаляются аккаунт жителя, его обращения и фотографии, переписка, показания и привязки к квартирам. Сами квартиры и данные других жильцов сохраняются. Отдельной кнопки удаления одного обращения нет. Если у жителя есть данные в домах вне доступа сотрудника, удалить весь аккаунт нельзя.

**Данные в мини-приложении.** Структура дома, обращения, сообщения, начисления и показания читаются из API и сохраняются в БД. Права доступа проверяются по квартирам пользователя. Создание обращений и сообщений использует `request_id`, чтобы повтор сетевого запроса не создавал дубликат. Доступ к фотографиям проверяется сервером.

## Настройки

Главный шаблон Docker — [`.env.docker.example`](.env.docker.example). `.env.docker` нужен Compose в корне; при запуске Python без Docker бот читает корневой `.env`, а API — `backend/.env`. Эти файлы не нужно коммитить.

| Переменная | Назначение |
| --- | --- |
| `POSTGRES_PASSWORD` | Пароль PostgreSQL в Docker. При уже созданном volume изменение переменной само по себе пароль БД не меняет. |
| `BOT_TOKEN` | Токен MAX; один и тот же у бота и API для проверки входа. |
| `MINI_APP_BOT_USERNAME` | Имя бота для кнопок открытия мини-приложения. |
| `YANDEX_API_KEY`, `YANDEX_FOLDER_ID` | Доступ бота к модели Yandex Cloud. |
| `ONBOARDING_TEST_MODE` | Создание демонстрационных домов и автоматическое принятие заявок; в корневом Compose по умолчанию `true`. |
| `LOCAL_SESSION_SECRET` | Секрет локального входа для разработки. |
| `NEXT_PUBLIC_API_BASE_URL` | Доступный **браузеру** адрес API с `/api/v1`; на одном HTTPS-сайте можно использовать `/api/v1`. Встраивается при сборке frontend. |
| `CORS_ORIGINS` | JSON-массив разрешённых адресов frontend. |
| `FRONTEND_PORT`, `API_PORT` | Локальные порты frontend и API. |
| `SESSION_COOKIE_SECURE` | `false` для локального HTTP, `true` для HTTPS. |
| `FORWARDED_ALLOW_IPS` | Доверенный адрес reverse proxy перед API. |

Дополнительный `SAMPLE_DATA_ENABLED` относится к старым, явно запускаемым демонстрационным данным и не должен использоваться как способ регистрации жителя. Для новой регистрации работает каталог УК и `ONBOARDING_TEST_MODE`. Секреты нельзя записывать в `NEXT_PUBLIC_*`: эти значения видны браузеру.

## Проверка изменений

Состояние и логи контейнеров:

```powershell
docker compose --env-file .env.docker -f compose.yaml -f compose.local.yaml --profile bot ps -a
docker compose --env-file .env.docker -f compose.yaml -f compose.local.yaml --profile bot logs --tail=100 api frontend bot
```

Если бот не запускали, в командах выше уберите `--profile bot` и `bot` из списка логов. `GET /health/ready` должен вернуть HTTP 200 и `{"status":"ok"}`. Запрос `/api/v1/me` без входа должен вернуть 401 — это ожидаемая защита.

Проверки кода выполняются из соответствующих каталогов после установки зависимостей:

```powershell
# Из mini-app/: сначала npm ci
npm run lint
npm run typecheck
npm test
npm run build

# Из backend/: после установки requirements-dev.txt
python -m ruff check .
python -m pytest -q
```

Для тестов миграций PostgreSQL нужен `TEST_POSTGRES_URL` отдельной тестовой базы; без него соответствующие тесты пропускаются. После изменения моделей применяйте миграции Alembic; корневой Compose делает это отдельным сервисом `migrate` до старта API.

## Публикация и работа команды

Для публичного запуска нужны HTTPS, Nginx, URL мини-приложения в настройках MAX и отдельные рабочие секреты. Серверный вариант использует `compose.yaml` вместе с `compose.production.yaml`, без локального override. Nginx направляет `/api/` и `/staff` в FastAPI, остальные пути — в Next.js. PostgreSQL не публикуется наружу. Перед обновлением с изменениями БД сохраните резервную копию PostgreSQL и тома с фотографиями; затем пересоберите сервисы и проверьте миграции и `/health/ready`. Подробнее о контейнерах — в [`DOCKER.md`](DOCKER.md), о серверной схеме — в [`deploy/README.md`](deploy/README.md).

Рабочий цикл команды: получить последние изменения, сделать небольшую часть, проверить её, посмотреть `git status` и `git diff`, затем создать понятный коммит. Перед сдачей хакатона зафиксируйте hash версии, которую показываете жюри:

```powershell
git status
git diff --check
git rev-parse HEAD
```

`git rev-parse HEAD` выводит идентификатор уже созданного коммита. Его можно передать вместе со ссылкой на репозиторий и работающим приложением. Секреты, файл БД и фотографии в коммит не входят.

## Что пока демонстрационное

- Оплата ЖКХ выглядит как интерфейс QR-кода и тестовой карты, но платёжный провайдер не подключён: списания нет. Показания счётчиков не пересчитывают выставленную квитанцию.
- Регистрация принимает только УК, дома и квартиры из каталога БД. Свободный ввод нового адреса, проверка адреса через внешний сервис и доказательство проживания пока не реализованы. Автопринятие заявок предназначено для тестового режима.
- Камеры показывают доступные кадры и их состояние; прямого видеопотока нет.
- «Здоровье дома» рассчитывается по обращениям, а не по показаниям инженерных датчиков.
- Уведомления в MAX требуют работающего бота; браузерные push-уведомления не реализованы.

Для обычной остановки локального проекта используйте `docker compose --env-file .env.docker -f compose.yaml -f compose.local.yaml --profile bot down`. Тома PostgreSQL и фотографий при этом сохраняются. Ключ `-v` удаляет тома и для обычной остановки не нужен.
