# ДомПульс

Мини-приложение и бот в MAX для жителей многоквартирного дома. Житель выбирает место проблемы, создаёт обращение и смотрит его статус. Также доступны план дома, переписки между квартирами, квитанции и передача показаний счётчиков.

## Устройство проекта

| Каталог | Назначение |
| --- | --- |
| `mini-app/` | Next.js, React, TypeScript, CSS Modules; интерфейс жителя |
| `backend/` | FastAPI, HTTP API, кабинет сотрудника УК, миграции Alembic и проверки |
| `chatbot/` | Бот MAX: регистрация, создание обращений, фотографии |
| `app/` | Общие модели SQLAlchemy и сервисы бота и API |
| `deploy/` | Настройки reverse proxy и инструкция развёртывания |

Мини-приложение обращается к API через `fetch`. API и бот работают с общей PostgreSQL через асинхронные сессии SQLAlchemy. Схему меняют миграции. Фотографии бота хранятся отдельно от БД.

Версии зависимостей закреплены в [requirements.txt](requirements.txt), [backend/requirements.txt](backend/requirements.txt) и [package-lock.json](mini-app/package-lock.json). Docker использует Python 3.14, Node.js 22 и PostgreSQL 17.

## Запуск

Нужны Docker Engine с Linux-контейнерами, Docker Compose v2 и доступ к реестрам образов и пакетам. Создайте `.env.docker` по [.env.docker.example](.env.docker.example), если файла ещё нет. Заполните настройки:

| Переменная | Назначение |
| --- | --- |
| `POSTGRES_PASSWORD` | Собственный случайный пароль БД; для Compose используйте буквы, цифры, `_` и `-` |
| `LOCAL_SESSION_SECRET` | Отдельный случайный секрет локального входа |
| `BOT_TOKEN` | Токен своего бота MAX, общий для бота и API |
| `YANDEX_API_KEY`, `YANDEX_FOLDER_ID` | Доступ к модели Yandex Cloud для бота |
| `NEXT_PUBLIC_API_BASE_URL` | Адрес API для браузера, локально `http://localhost:8000/api/v1` |
| `CORS_ORIGINS` | JSON-массив разрешённых адресов frontend |
| `FRONTEND_PORT`, `API_PORT` | По умолчанию `3000` и `8000` |
| `SESSION_COOKIE_SECURE` | `false` для локального HTTP, `true` для HTTPS |
| `LOCAL_DOCKER_SUBNET` | Подсеть контейнеров для локального входа; меняется при конфликте сетей |

Из корня репозитория запустите все локальные компоненты, включая бот:

```sh
docker compose --env-file .env.docker -f compose.yaml -f compose.local.yaml --profile bot up -d --build
```

Запускаются PostgreSQL, миграции, создание локального жителя, API, frontend и бот. Для проверки только приложения без MAX и Yandex Cloud уберите `--profile bot`: внешние ключи в этом варианте не нужны.

Frontend: http://localhost:3000. API: http://localhost:8000, Swagger: http://localhost:8000/docs. PostgreSQL доступна только внутри Docker на порту `5432`. Локальный вход работает через `localhost` или `127.0.0.1`.

Подробности: [Docker](DOCKER.md), [backend](backend/README.md), [frontend](mini-app/README.md), [развёртывание с HTTPS](deploy/README.md).

## Внешние сервисы

MAX нужен для регистрации через бот и входа по подписанным данным запуска. Для проверки в MAX нужны собственный бот, настроенный URL мини-приложения и доступный HTTPS-сервер. Локальный браузерный вход не проверяет интеграцию с MAX. Бот использует polling; второй экземпляр с тем же токеном запускать не следует. Активная webhook-подписка препятствует запуску polling.

Yandex Cloud используется ботом для разбора текста обращения. Нужны API-ключ, каталог и разрешение на вызов модели. Форма мини-приложения не требует этого сервиса.

## Данные

PostgreSQL хранит пользователей, дома, квартиры, обращения и историю статусов, сообщения, квитанции и показания. API проверяет доступ по привязкам пользователя к квартирам. Секреты хранятся в локальных env-файлах вне Git и не передаются в `NEXT_PUBLIC_*`.

Локальный Compose вызывает `scripts.seed_local`: создаёт проверочного жителя, дом и квартиру. Это подготовленные данные для разработки. Обращения и сообщения после входа записываются в БД обычными запросами API.

Дополнительное заполнение включается явно через `SAMPLE_DATA_ENABLED=true` у API и бота. Оно назначает жителям до двух квартир в общем доме, добавляет тестовые начисления, приборы и обращения. Это не реальные лицевые счета и не подтверждение права собственности. Порядок заполнения описан в [backend README](backend/README.md#данные-для-проверки).

База и фотографии сохраняются в Docker volumes. Отключение заполнения не удаляет записи. Перенос существующих данных выполняется отдельно, после резервного копирования.

## Проверка основного сценария

1. Запустите локальный Compose и откройте `/health/ready`: ожидается HTTP 200 и `{"status":"ok"}`.
2. Откройте frontend и выберите локальный вход. Должны загрузиться профиль и квартира.
3. Нажмите «Сообщить о проблеме», выберите место и категорию, заполните описание. Вернитесь на предыдущий шаг: значения должны сохраниться.
4. Отправьте обращение. Должна открыться карточка с выбранным местом, описанием и статусом «Новое».
5. Откройте список и обновите страницу. Запись должна остаться. Повтор того же запроса не должен создавать дубликат.
6. Проверьте пустые обязательные поля: форма должна показать ошибку. При сетевой ошибке данные должны сохраниться для повторной отправки.
7. Проверьте desktop и ширину 320px: текст и кнопки должны помещаться без горизонтальной прокрутки.

Для проверки в MAX отправьте боту `/start`, подготовьте привязку квартиры и откройте мини-приложение кнопкой бота. Повторите создание и просмотр обращения в мобильной и веб-версиях MAX. Без сессии `/api/v1/me` возвращает 401; незарегистрированный пользователь не получает доступ к данным.

## Ограничения

- Оплата ЖКХ и обмен с поставщиками не подключены. Показания не пересчитывают уже выставленную квитанцию.
- Кабинет УК доступен на `/staff/`: [вход, создание сотрудников и запуск](backend/docs/staff-portal.md). Назначение отдельных исполнителей по заявкам пока не предусмотрено.
- Кабинет обновляет список и диалог каждые 20 секунд. Уведомления в MAX требуют работающего бота; браузерных push-уведомлений нет.
- Камеры показывают зарегистрированный источник кадра; видеотрансляции не реализованы.
- Здоровье дома рассчитывается по обращениям, а не по датчикам.
- Фотографии принимает бот; сотрудник смотрит их через защищённый API. Загрузка фото через мини-приложение пока отсутствует.
- Черновик формы хранится в памяти вкладки и не переживает перезагрузку.

## Остановка и повторный запуск

```sh
docker compose --env-file .env.docker -f compose.yaml -f compose.local.yaml --profile bot down
docker compose --env-file .env.docker -f compose.yaml -f compose.local.yaml --profile bot up -d --build
```

`down` сохраняет volumes. Параметр `-v` удаляет данные и для обычной остановки не нужен. Состояние контейнеров и логи: [DOCKER.md](DOCKER.md).

## Проверки и материалы для сдачи

В `mini-app`: `npm run lint`, `npm run typecheck`, `npm test`, `npm run build`. В `backend`: `python -m ruff check .`, `python -m pytest -q`; настройка окружения описана в README компонентов.

Контракт API: [openapi.json](backend/openapi.json). [DATA-API.yaml](backend/DATA-API.yaml) содержит черновик проверок: перед сдачей нужно согласовать формат с организаторами и добавить проверки авторизованного сценария. Для передачи решения также нужны ссылка на приложение в MAX, hash выбранного коммита и доступ проверяющего к подготовленным данным. Рабочие реквизиты передаются отдельно от публичного репозитория.
