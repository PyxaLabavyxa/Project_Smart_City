# Домовед API

FastAPI и асинхронный SQLAlchemy с PostgreSQL. API и бот используют модели из `app/database/models.py`; схема управляется Alembic. Общий запуск: [DOCKER.md](../DOCKER.md).

## Запуск без Docker

Нужны Python 3.14 и PostgreSQL 17. Создайте базу и пользователя, затем `backend/.env` по [.env.example](.env.example). Существующий env-файл не заменяйте.

Из каталога `backend`, PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
$env:PYTHONPATH = ".."
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m uvicorn smart_city_api.main:app --host 127.0.0.1 --port 8000 --loop smart_city_api.runtime:loop_factory
```

Перед миграцией заполните `DATABASE_URL`. На Linux используйте `.venv/bin/python` и `export PYTHONPATH=..`. Фабрика цикла событий обеспечивает работу Psycopg на Windows. Остановка — Ctrl+C; повторный запуск — та же команда Uvicorn.

| Переменная | Назначение |
| --- | --- |
| `DATABASE_URL` | PostgreSQL URL с драйвером `postgresql+psycopg`; пароль в URL должен быть закодирован |
| `BOT_TOKEN` | Тот же токен, что у бота |
| `CORS_ORIGINS` | JSON-массив разрешённых origins frontend |
| `SESSION_COOKIE_SECURE` | `true` для HTTPS |
| `MAX_AUTH_AGE_SECONDS` | Допустимый возраст данных MAX, по умолчанию 3600 секунд |
| `LOCAL_LOGIN_ENABLED` | Включение локального входа, по умолчанию выключен |
| `LOCAL_SESSION_SECRET` | Серверный секрет локальной сессии |
| `SAMPLE_DATA_ENABLED` | Заполнение подготовленных данных, по умолчанию выключено |
| `POSTGRES_PASSWORD`, `COMPOSE_DATABASE_URL` | Настройки отдельного `backend/compose.yaml` |

Бот получает тот же `DATABASE_URL` из корневого `.env`. Бот и API не создают таблицы PostgreSQL при старте: сначала нужны миграции.

## Авторизация

`POST /api/v1/auth/max` проверяет подпись и возраст данных запуска MAX, находит пользователя бота и устанавливает HttpOnly-cookie. Сессия действует один час. Запросы на запись проверяют Origin; доступ к данным — привязки квартир. Также поддерживается `Authorization: Bearer <подписанная initData>`.

Без авторизации API возвращает 401, для незарегистрированного пользователя — 403. Открытой регистрации через API нет: сначала нужен `/start` в боте.

Для локального входа задайте `LOCAL_LOGIN_ENABLED=true` и случайный `LOCAL_SESSION_SECRET` на сервере, `NEXT_PUBLIC_ENABLE_LOCAL_LOGIN=true` у frontend. С подготовленным окружением выполните:

```sh
python -m scripts.seed_local
```

Команда создаёт проверочного жителя, дом и квартиру; повторный запуск сохраняет записи. Локальный вход ограничен разрешённой сетью и Origin. Вне Docker по умолчанию разрешён loopback; локальный Compose отдельно задаёт свою подсеть. На публичном сервере этот режим должен быть выключен.

## Данные для проверки

`SAMPLE_DATA_ENABLED=true` включает подготовку данных при регистрации через бот и загрузке профиля API. Флаг задаётся каждому процессу отдельно. Житель получает до двух квартир в общем доме, тестовые счета, приборы и обращения. Распределение старается выдать по квартире в разных подъездах, повторное обращение сохраняет привязки. Исходная структура — 15 этажей и два подъезда; при заполнении добавляется подъезд.

Для заполнения уже зарегистрированных жителей выполните из `backend` с настроенными `DATABASE_URL`, `SAMPLE_DATA_ENABLED=true` и `PYTHONPATH`:

```sh
python -m scripts.seed_residents
```

Это синтетические данные, включая начисления и тарифы. Платежи не проводятся. Отключение флага прекращает заполнение, но не удаляет записи. Frontend получает их из PostgreSQL через API, а не подменяет ответы.

## Маршруты и данные

Контракт: [openapi.json](openapi.json). При запуске доступны `/docs` и `/openapi.json`.

| Путь | Назначение |
| --- | --- |
| `/api/v1/me` | Профиль, квартиры и дома |
| `/api/v1/houses/{id}/apartments` | Квартиры, подъезды и этажи |
| `/api/v1/houses/{id}/issues` | Чтение и создание обращений |
| `/api/v1/issues/{id}` | Карточка обращения и история |
| `/api/v1/apartments/{id}/messages` | История и отправка сообщений |
| `/api/v1/apartments/{id}/utilities` | Лицевой счёт, квитанция, приборы |
| `/api/v1/meters/{id}/readings` | Передача показаний |
| `/api/v1/houses/{id}/cameras` | Камеры дома |
| `/api/v1/cameras/{id}/preview` | Доступный кадр камеры |
| `/api/v1/houses/{id}/works` | Работы дома |
| `/api/v1/houses/{id}/contacts` | Контакты УК для жителей дома |
| `/health/live`, `/health/ready` | Работа процесса и соединение с БД |

Списки обращений, сообщений и квартир поддерживают cursor-пагинацию. Создание обращения и сообщения использует UUID `request_id`: повтор с тем же содержимым возвращает запись, с другим — 409.

Обращения в квартире доступны её жильцам и автору, общие — жильцам дома. Старые обращения без места считаются общедомовыми; при импорте нужно проверить их содержимое. История содержит только записанные изменения.

Состав приборов и квитанции задаются серверными данными. Деньги хранятся в копейках, показания — Decimal. Показание не пересчитывает выставленную квитанцию. Изменение уже принятого показания возвращает 409.

Кабинет УК: `/staff/`, API: `/api/v1/staff`. Есть вход по логину/паролю, назначения домов, таблица и фото, смена статуса с уведомлением в MAX и переписка с автором. Создание сотрудников и запуск: [инструкция](docs/staff-portal.md). Замечания к архитектуре: [обзор](docs/architecture-review.md).

В разделе «Контакты» кабинета УК выберите назначенный дом, добавьте до 12 телефонов, адресов электронной почты, адресов приёмной или ссылок на сайт и нажмите «Сохранить контакты». Примечание подходит для часов работы. Контакты хранятся в `house_contacts`, название УК берётся из привязки дома к компании. GET/POST `/api/v1/staff/houses/{id}/contacts` доступны только назначенным сотрудникам; запись защищена CSRF. Жители получают контакты только своих домов через GET `/api/v1/houses/{id}/contacts`. Сохранение заменяет весь список, пустой список удаляет контакты.

Перед запуском обновлённого API примените миграцию `0007`: из `backend` выполните `python -m alembic upgrade head` с настроенным `DATABASE_URL`. Миграция добавляет таблицу контактов и сохраняет существующие данные. При пустом списке мини-приложение показывает, что УК ещё не добавила контакты.

Не реализованы приём платежей, обмен с поставщиками, видеотрансляции и HTTP-загрузка фотографий. Пустая таблица возвращает пустой результат.

## Перенос SQLite

Остановите запись бота и сохраните резервную копию SQLite, включая WAL/SHM при наличии. Подготовьте пустую PostgreSQL и примените миграции. Из `backend`, с настроенным `PYTHONPATH`:

```sh
python -m scripts.import_sqlite /path/to/source.db
```

Замените путь на свой. Скрипт читает исходную БД в read-only режиме и переносит пользователей, дома, квартиры, связи, обращения и фотографии одной транзакцией с сохранением ID. Импорт в непустую БД запрещён. Сами фотографии перенесите отдельно в `MEDIA_ROOT`. Даты SQLite без часового пояса интерпретируются как UTC. После проверки задайте новый `DATABASE_URL` обоим сервисам.

## Проверки

В подготовленном окружении из `backend`:

```sh
python -m ruff check .
python -m pytest -q
python -m pip check
python -m scripts.export_openapi
```

Для PostgreSQL-проверок задайте `TEST_POSTGRES_URL` отдельной проверочной БД с драйвером `postgresql+psycopg`. Тесты создают и удаляют схемы `qa_*`. Без этой переменной соответствующие проверки пропускаются; остальные используют временную SQLite.

Проверяются авторизация, права доступа, повторная отправка, показания, миграции и импорт. Пользовательский сценарий описан в [корневом README](../README.md#проверка-основного-сценария).

[DATA-API.yaml](DATA-API.yaml) — черновик материалов для проверки, а не согласованная схема организаторов. Перед сдачей нужны публичный HTTPS-адрес, проверки авторизованного сценария и отдельная передача доступа проверяющему.
