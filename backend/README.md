# Домовед API

Backend на FastAPI и SQLAlchemy с PostgreSQL. API и бот используют общие модели из `app/database/`; схема базы обновляется через Alembic. Кабинет УК расположен в `smart_city_api/staff_web/` и доступен по `/staff/`.

Запуск проекта в Docker описан в [DOCKER.md](../DOCKER.md).

## Запуск без Docker

Требуются Python 3.14 и PostgreSQL 17. Создайте базу и пользователя, скопируйте [.env.example](.env.example) в `.env` и заполните настройки. Если `.env` уже существует, используйте его.

Из каталога `backend` в PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
$env:PYTHONPATH = ".."
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m uvicorn smart_city_api.main:app --host 127.0.0.1 --port 8000 --loop smart_city_api.runtime:loop_factory
```

На Linux используйте `.venv/bin/python` и `export PYTHONPATH=..`. Документация API доступна по `/api/docs`, актуальный контракт — по `/api/openapi.json`. Проверка подключения к базе: `/health/ready`.

## Камеры жителей

`POST /api/v1/houses/{house_id}/cameras` принимает название, описание, `source_url` (HTTPS-снимок), `is_public`, `place` в формате места обращения и UUID `request_id`. Повтор с тем же ключом и данными возвращает ту же камеру; изменение данных под тем же ключом возвращает 409. Место проверяется по дому пользователя; внутри квартиры разрешена только своя квартира.

Список и `/api/v1/cameras/{id}/preview` применяют одинаковые права: личные, ожидающие и отклонённые камеры доступны владельцу, одобренные общедоступные — жителям дома. Адрес источника не включается в список камер. API не загружает пользовательские URL на сервере: снимок получает браузер после проверки доступа к камере. Источник должен быть доступен с устройства пользователя и разрешать показ снимка; срок действия подписанной ссылки и кеширование задаются источником.

В кабинете УК раздел «Камеры» показывает существующие общедоступные камеры и заявки только назначенных сотруднику домов. `GET /api/v1/staff/cameras` поддерживает статусы `all`, `pending` (по умолчанию в API), `approved`, `rejected` и пагинацию; интерфейс изначально показывает все камеры. У камер дома без владельца отображается «Камера дома», источник снимка может отсутствовать. `POST /api/v1/staff/cameras/{id}/moderate` принимает `decision` (`approved`/`rejected`) и обязательную для отклонения `reason`. Действуют существующие сессии и CSRF. Решение, сотрудник и время сохраняются; конфликтующее повторное решение возвращает 409. Личные камеры сотрудникам не показываются.

`DELETE /api/v1/staff/cameras/{id}` удаляет общедоступную камеру назначенного дома из интерфейса сотрудника, списка жителей и доступа к снимку. Повторное удаление возвращает 204. Запись сохраняется с `deleted_at`, чтобы демоданные не создавали удалённые камеры заново; повтор создания с исходным `request_id` возвращает 409. Миграция `0012` добавляет только nullable-поле и сохраняет существующие камеры. Откат до `0011` блокируется при наличии удалённых камер, чтобы не вернуть их в приложение старой версии; при откате приложения также следует сохранить поддержку этого поля.

В таблице статус и «Управление» разделены: выпадающий список предлагает одобрение/отклонение ожидающих заявок и удаление с подтверждением. Фильтры `house_id`, `entrance`, `floor`, `zone` применяются совместно до подсчёта и пагинации; выбранный дом не расширяет права сотрудника. По умолчанию `page_size=5`, интерфейс показывает по 5 камер и сбрасывает страницу при смене фильтров. Количество подъездов и этажей берётся из геометрии назначенных домов в `/api/v1/staff/me`.

Миграция `0011` сохраняет существующие камеры общедоступными и одобренными, заполняет места стандартных тестовых камер. Перед обновлением сохраните резервную копию БД. Обратная миграция допускается, только если нет камер жителей: иначе она останавливается, чтобы не потерять настройки приватности и не открыть личные камеры старой версии приложения. Архивация/удаление камер жителей перед откатом требует отдельного решения администратора.

## Авторизация и регистрация

`POST /api/v1/auth/max` проверяет подписанные параметры MAX, создаёт пользователя при первом входе и выдаёт HttpOnly-cookie на один час. Также поддерживается `Authorization: Bearer <initData>`. Без авторизации защищённые маршруты возвращают 401.

`GET /api/v1/registration` возвращает состояние регистрации и каталог УК. `POST` принимает ФИО, УК, дом и номер квартиры. При `ONBOARDING_TEST_MODE=true` заявка принимается автоматически; иначе её рассматривает сотрудник. Пользователь может добавить несколько квартир, а одну квартиру могут привязать несколько жильцов.

Доступ к данным определяется привязками квартир. Обращения во дворе видны всем жильцам дома, в подъезде — жильцам этого подъезда, в квартире — только автору, даже если в квартире зарегистрированы другие пользователи. Автор также видит собственные обращения в других подъездах своего дома. Для просмотра требуется действующая привязка к дому. Старые обращения без указанного места, включая созданные через бота, доступны только автору. Сотрудники УК видят все обращения назначенных им домов. Эти правила действуют для списков, карточек и фотографий; прямые ссылки не обходят проверку. Запросы на запись с cookie-сессией проверяют Origin.

## Основные маршруты

Пути в таблице указаны относительно `/api/v1`.

| Путь | Назначение |
| --- | --- |
| `/me` | Профиль, квартиры и дома пользователя |
| `/houses/{id}/apartments` | Структура квартир по подъездам и этажам |
| `/houses/{id}/issues` | Список и создание обращений |
| `/houses/{id}/issues/with-photos` | Создание обращения с фотографиями |
| `/issues/{id}` | Карточка и история обращения |
| `/issues/{id}/messages` | GET: переписка автора с УК; POST: сообщение до 1500 символов с UUID `request_id` |
| `/issues/{id}/presence` | Присутствие в конкретном чате и подтверждение прочитанных сообщений |
| `/issues/{id}/photos/{photo_id}` | Фотография обращения |
| `/apartments/{id}/messages` | Чтение и отправка сообщений |
| `/apartments/{id}/utilities` | Лицевой счёт, квитанция и приборы |
| `/meters/{id}/readings` | Передача показаний |
| `/houses/{id}/cameras`, `/cameras/{id}/preview` | Камеры и доступные кадры |
| `/houses/{id}/works`, `/houses/{id}/contacts` | Работы по дому и контакты УК |
| `/staff` | API кабинета сотрудника |

Списки квартир, обращений и сообщений используют cursor-пагинацию. При создании обращений и сообщений передаётся UUID `request_id`: повтор с тем же содержимым возвращает существующую запись, с другим — ошибку 409.

Переписка по обращению доступна только его автору с действующей привязкой к дому; остальным жильцам, включая жильцов той же квартиры, API возвращает 404. Отклонённые обращения недоступны, по решённым можно задать уточнение. Сообщения сохраняются в общей таблице `issue_messages`: кабинет УК и мини-приложение видят одну историю, в том числе ответы, ранее отправленные через бота. Бот доставляет уведомления и ссылки `?startapp=issue_<id>`, переписка ведётся в мини-приложении.

Миграция `0009` добавляет область чата в `mini_app_presence` и `staff_notifications.suppressed_at`. Видимый чат продлевает присутствие раз в 10 секунд; срок действия — 30 секунд. `last_message_id` подтверждает видимые сообщения и навсегда отменяет соответствующие уведомления. Пока чат открыт, непрочитанные сообщения ожидают подтверждения; при выходе или истечении присутствия бот доставляет оставшиеся. Общий вход в мини-приложение и другой чат не заглушают сообщения УК. Уведомления о статусах отправляются независимо от присутствия. В кабинете УК такие сообщения отмечены «Прочитано в мини-приложении» (`delivery: read`).

## Кабинет УК

Сотрудник входит по логину и паролю и работает только с назначенными домами: рассматривает обращения и заявки на квартиры, меняет статусы, отправляет сообщения и редактирует контакты. Отклонение обращения требует причины: обращение скрывается из списков, бот отправляет автору уведомление. В принятых заявках доступно удаление аккаунта вместе с его обращениями и привязками; общие данные дома и аккаунты других жильцов сохраняются. Удаление недоступно, если у пользователя есть данные в домах другой УК.

В контактах отображаются назначенные сотруднику дома зарегистрированных УК. Тестовые дома получают демонстрационные номера, которые можно заменить в редакторе. Уведомления жителям доставляет бот.

Создание сотрудника из каталога `backend`:

```powershell
python -m scripts.manage_staff list
python -m scripts.manage_staff create manager --name "Сотрудник УК" --house 1 --house 2
```

Команда запросит пароль в терминале. Укажите ID существующих домов. Для изменения назначений используется `assign`; он заменяет список домов целиком.

### MAX-чаты и объявления

В разделе «MAX-чаты» сотрудник подключает по одной группе к каждому назначенному дому. Бота нужно предварительно разрешить добавлять в группы в настройках MAX и выдать права администратора на чтение, отправку и закрепление сообщений. Кабинет выдаёт одноразовую команду `/domoved <код>` на 15 минут; её отправляет администратор нужной группы. Новый код отменяет предыдущий. После проверки бот публикует и закрепляет одно приветствие с кнопками мини-приложения. Восстановление меню использует прежнее сообщение, если оно сохранилось.

В «Рассылках» сотрудник сохраняет черновик, выбирает дома и проверяет окончательный текст и получателей перед отправкой. Доставка разрешена только в подключённые исправные чаты. История показывает результат отдельно для каждого дома; повторная команда отправки не дублирует уже поставленную рассылку. При неопределённом результате MAX автоматический повтор отключён: сначала нужно проверить группу. При отключении чата ещё не начатые отправки отменяются; уже начавшийся запрос может завершиться.

Бот не отвечает на обычную переписку группы и не публикует туда обращения, статусы, фотографии или личные сообщения. Объявления создаёт сотрудник вручную. Можно выбрать домовые группы, личные сообщения жителям выбранных домов или конкретных жителей своей УК; оба канала доступны для аудитории домов. Адресное сообщение отдельным жителям отправляется только лично. В предпросмотре фиксируется точный список получателей, повторные квартиры одного жителя не дублируют личное сообщение. Перед постановкой в очередь и отправкой заново проверяются права сотрудника, привязка жителя и настройка «Объявления».

Личная доставка доступна после подтверждённого взаимодействия с ботом. Миграция `0014` сохраняет этот признак по прежним заявкам через бота и подтверждённым личным уведомлениям; один вход в мини-приложение таким подтверждением не считается. Последующие личные события и остановка бота обновляют признак. Неопределённый результат личной отправки также не повторяется автоматически. Личные рассылки не требуют подключения домового чата. Миграции `0013`–`0014` хранят подключения и очереди, доставку выполняет процесс бота. Отслеживания источника перехода нет. Работа в настоящей группе требует проверки после разрешения группового доступа со стороны MAX.

## Материалы проверки API

Команда — **«Облачный Код»**, решение — **«Домовед»**. Публичный базовый адрес: **https://201.34.159.33/api/v1**. [Swagger](https://201.34.159.33/api/docs) позволяет выполнять запросы; для жителя и сотрудника предусмотрены отдельные схемы авторизации.

[openapi.yaml](evaluation/openapi.yaml) и [openapi.json](evaluation/openapi.json) в `evaluation/` содержат контракт проверяемой версии API, включая чат и присутствие в обращении. Файлы в корне `backend` описывают локальное приложение. Тесты проверяют актуальность локального контракта и совместимость с сохранённым снимком. После развёртывания подтвердите совпадение публичного контракта с экспортом. Обновление из каталога `backend` после установки зависимостей разработки и настройки `PYTHONPATH`:

```powershell
python -m scripts.export_openapi
python -m scripts.export_openapi --public-url https://201.34.159.33/api/openapi.json
```

[DATA-API.yaml](DATA-API.yaml) описывает 26 последовательных проверок с параметрами, ролями, кодами ответа и JSON Schema. Версия `1.0` относится к собственному формату команды, заданному [DATA-API.schema.json](DATA-API.schema.json): отдельный шаблон платформы проверки не предоставлен. Относительные пути прибавляются к базовому адресу: `/me` означает `https://201.34.159.33/api/v1/me`. Служебные проверки `/health/live` и `/health/ready` используют полные адреса вне `/api/v1`.

[test-data.json](test-data.json) содержит синтетические данные и тела запросов. Тест `tests/test_evaluation_materials.py` создаёт временную базу из этих данных и выполняет все проверки DATA-API, проверяя коды ответа и JSON-структуру. ID из fixture предназначены только для этой базы; для публичной проверки нужно подставить ID выделенных тестовых объектов, текущий открытый период показаний и новые UUID запросов. Проверки POST создают обращения, сообщения, заявку на дополнительную квартиру, меняют статус обращения, контакты тестового дома и показания.

[test-accounts.example.json](test-accounts.example.json) — шаблон предоставления доступа, а не готовые учётные записи публичного сервера. Проверяющему нужны тестовый житель MAX с привязанной квартирой и сотрудник с доступом к тому же тестовому дому. Реальные логин, пароль и свежая подписанная `initData` передаются отдельно; административный доступ для этих сценариев не нужен. Сотрудник входит через `POST /api/v1/staff/auth/login`: HTTP-клиент сохраняет cookie, а для изменяющих запросов передаёт `Origin` и `X-CSRF-Token` из ответа `GET /api/v1/staff/me`. Для API-клиентов доступен `POST /api/v1/staff/auth/token`: токен из `access_token` передают в `Authorization: Bearer`. Проверки DATA-API используют cookie-вход; сайт УК продолжает работать через cookie и CSRF.

## Проверки

```powershell
python -m ruff check .
python -m pytest -q
python -m pip check
```

Для тестов PostgreSQL задайте `TEST_POSTGRES_URL` отдельной тестовой базы. Без этой переменной соответствующие тесты пропускаются. После изменения моделей примените `python -m alembic upgrade head`.

`GET /api/v1/me/notifications` читает настройки уведомлений текущего жителя; `POST` по тому же адресу сохраняет четыре логических поля: `personal_messages`, `issue_messages`, `issue_statuses`, `announcements`. Очереди личных уведомлений MAX проверяют настройки перед отправкой; отключённые уведомления не отправляются повторно после включения. Миграция `0010` включает все категории для существующих пользователей. Личные объявления учитывают `announcements`; публикации в общих группах подчиняются настройкам уведомлений самой группы в MAX.

Платёжный провайдер и видеотрансляции не подключены. Передача показаний не пересчитывает выставленную квитанцию.
