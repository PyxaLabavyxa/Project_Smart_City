# План API

Исторический план развития. Реализованные маршруты перечислены в ../README.md
и ../openapi.json; таблицы ниже включают будущие операции и не являются контрактом.

## Что есть в БД чатбота

Источник: `../Project_Smart_City/app/database/models.py` и `enums.py`.

| Таблица | Что можно использовать |
| --- | --- |
| users | Внутренний ID, уникальный max_user_id, имя |
| houses | Адрес, число подъездов, этажей и квартир на типовом этаже |
| apartments | Реальный ID квартиры, номер, подъезд, этаж, house_id |
| user_apartments | Доступ пользователя к одной или нескольким квартирам |
| issues | Автор, дом, заголовок, описание, категория, статус, приоритет, дата |
| issue_photos | Привязка файла к обращению |

Сейчас бот использует async SQLAlchemy + aiosqlite, URL по умолчанию
`sqlite+aiosqlite:///./data/smart_city.db`. Относительный путь зависит от cwd;
нельзя копировать его в другой сервис и рассчитывать на ту же БД.
Модуль `app.database.session` импортировать в API нельзя: он загружает
конфигурацию бота и требует BOT_TOKEN и ключи ИИ.

Бот и API импортируют общие ORM-модели из app/database/models.py.
Схема PostgreSQL управляется Alembic, изменения при старте не выполняются.
Реализованы проверка подписи MAX, HttpOnly-сессия и проверки доступа через
user_apartments. Дальнейшие изменения схемы выполняются отдельными миграциями.

## Порядок реализации

### 1. Авторизация, пользователь, дом

| Метод и путь | Назначение |
| --- | --- |
| POST /auth/max | Проверить данные запуска MAX на сервере и выдать сессию |
| DELETE /auth/session | Завершить текущую сессию |
| GET /me | Пользователь и его доступные квартиры |
| GET /me/houses | Дома пользователя через user_apartments, без повторов |
| GET /houses/{house_id} | Адрес и общие сведения доступного дома |
| GET /houses/{house_id}/structure | Структура для фасада и выбора этажей |
| GET /houses/{house_id}/apartments | Квартиры; фильтры entrance, floor, number |

Формат MAX-авторизации нужно согласовать с реальным Bridge и официальным
протоколом проверки. Не принимать max_user_id, user_id или номер квартиры
от клиента как доказательство личности. Не добавлять обход авторизации
через query/header. До этого бизнес-данные не открывать наружу.

Выбранный дом — UI-состояние, отдельный POST для его переключения не нужен.
Структура и квартиры только для чтения. Номера брать из apartments, а не
восстанавливать клиентской формулой: в реальном доме возможны исключения.
Чужие имена и контакты по списку квартир не выдавать. Детали связи пользователя
с квартирой доступны только ему.

### 2. Основной сценарий обращений

| Метод и путь | Назначение |
| --- | --- |
| GET /issue-options | Разрешённые категории, приоритеты, статусы и подписи |
| GET /houses/{house_id}/issues | Список: mine, status, category, entrance, floor, q, cursor, limit |
| POST /houses/{house_id}/issues | Создание с местом, категорией, описанием и ключом идемпотентности |
| GET /issues/{issue_id} | Карточка, место, история и доступные действия |
| GET /houses/{house_id}/issues/similar | Активные похожие обращения по месту и категории |
| POST /issues/{issue_id}/photos | Загрузка фото с проверкой формата, размера и доступа |
| GET /issues/{issue_id}/photos/{photo_id} | Авторизованное чтение фотографии, без file_path в JSON |
| POST /issues/{issue_id}/resolution-response | Подтвердить решение или вернуть в работу, когда появится workflow |

Добавить к БД: место обращения (zone, entrance, floor, apartment_id при наличии),
историю изменений, серверную идемпотентность создания и необходимые поля
подтверждения решения. Историю писать в той же транзакции, что и статус.
Нельзя восстановить настоящую историю из одного текущего status.

Текущие enum БД:
- категории: water, heating, electricity, elevator, entrance, yard, garbage, security, other;
- статусы: new, in_progress, resolved;
- приоритеты: HIGH=1, MEDIUM=2, LOW=3.

SQLAlchemy Enum по умолчанию хранит имена элементов (`NEW`, `HIGH`), не их
значения. В JSON сериализовать явно согласованные значения, не менять хранение
без миграции. Frontend in-progress/completed преобразовывать на границе API.
accepted/assigned/awaiting-confirmation и cleaning сейчас существуют только
во frontend: их необходимо отдельно согласовать, а не молча подменять.
Права на обращения дома и приватные обращения внутри квартиры нужно разделить.
Житель не получает общий PATCH произвольного статуса или приоритета.

### 3. ЖКХ

| Метод и путь | Назначение |
| --- | --- |
| GET /apartments/{apartment_id}/utility-accounts | Лицевые счета своей квартиры по поставщикам |
| GET /utility-accounts/{account_id}/invoices | Квитанции по периодам, страницы |
| GET /invoices/{invoice_id} | Начисления, перерасчёт, долг, пени, срок, остаток |
| GET /utility-accounts/{account_id}/meters | Зарегистрированные приборы и разрешённые периоды передачи |
| GET /meters/{meter_id}/readings | История показаний |
| POST /meters/{meter_id}/readings | Показание, дата снятия, период; валидация на сервере |
| POST /invoices/{invoice_id}/payment-intents | Начать оплату QR/картой у провайдера |
| GET /payments/{payment_id} | Проверить состояние платежа |
| POST /webhooks/payments/{provider} | Подписанное уведомление провайдера, не пользовательский маршрут |

Новые сущности: лицевые счета, поставщики, приборы, тарифные регистры
(электричество может быть многотарифным), показания, квитанции, строки
начислений, платежи, события провайдера. Детали схемы согласовать при реализации.
Деньги — integer в копейках или NUMERIC, объёмы — Decimal; не float.
Выставленная квитанция неизменяема от новых показаний следующего периода.
Проверять владение квартирой через user_apartments для каждого вложенного ID.
Приборы/номера/тарифы приходят от обслуживающей организации, не создаются жителем.
Уникальность показаний по прибору, регистру и периоду должна обеспечиваться БД;
исправления, поверку, замену и сброс счётчика нужно обработать отдельно.

Сумму, получателя и реквизиты платежа определяет сервер из квитанции.
PAN/CVV не принимаются и не хранятся в этом API: настоящая форма должна быть
у платёжного провайдера. Кнопка «оплачено» не подтверждает платёж.
Нужны подпись webhook, проверка суммы/валюты/заказа и идемпотентная обработка.
Платёжные endpoints не реализовывать, пока не выбран провайдер и контракт.

### 4. Переписки и остальные экраны

| Метод и путь | Назначение |
| --- | --- |
| GET /conversations | Переписки, последние сообщения, страницы |
| POST /conversations | Открыть/найти разговор своей квартиры с соседней |
| GET /conversations/{id}/messages | История с cursor |
| POST /conversations/{id}/messages | Сообщение с ключом идемпотентности |
| PUT /conversations/{id}/read-position | Последнее прочитанное сообщение |
| GET /houses/{house_id}/health | Показатель здоровья и связанные проблемы |
| GET /houses/{house_id}/works | Плановые работы |
| GET /houses/{house_id}/cameras | Доступные камеры и состояния |
| GET /cameras/{camera_id} | Карточка камеры |
| GET /cameras/{camera_id}/preview | Авторизованный кадр или краткоживущая ссылка |

Переписка требует conversation, участников и messages; доступ только участникам,
разрешённым через квартиры. Номер квартиры сам по себе не уникален между домами.
WebSocket, уведомления и read receipts — после обычной HTTP-истории и отправки.
Здоровье дома сейчас — клиентский расчёт по условным обращениям; это не датчики.
Камеры и работы потребуют отдельных источников, модели и правил доступа.

## Общие соглашения будущего контракта

- Внутренние PK — integer, ISO 8601 UTC для времени; локализация во frontend.
- Cursor-пагинация, limit по умолчанию 20, максимум 100; стабильный порядок date/id.
- DTO отделены от ORM: не отдавать max_user_id, пути файлов, ключи камер, чужие контакты.
- Единые бизнес-ошибки: code, message, field_errors, request_id; 401/403/404/409/422.
  Сейчас служебные 503 используют обычный FastAPI detail.
- Транзакции и ограничения БД обязательны; клиентская валидация не защита.
- Rate limits для авторизации, создания обращений, сообщений и начала оплаты.
- Для POST повтор запроса не должен создавать дубликаты. Ключ идемпотентности
  привязывается к пользователю, маршруту и содержимому запроса.
- SQLite подходит текущей локальной разработке. Перед совместной нагрузкой
  бота/API оценить PostgreSQL; сейчас драйвер и миграцию не добавляем.
