# Архитектура после добавления кабинета

Разделение на `chatbot`, `backend`, `mini-app` и общий `app` подходит нынешнему размеру проекта. Уже есть общие модели, Alembic, отдельные HTTP-схемы и сервисы, проверка доступа жителя и закреплённые зависимости. Полная перестройка каталогов сейчас не нужна.

## Что улучшить следующим шагом

1. **Единая конфигурация путей и БД.** Бот читает корневой `.env` через environs, backend — `.env` текущего каталога через pydantic-settings. Фабрики сессий тоже создаются отдельно. При запуске из другого каталога можно получить разные БД. Для нового кабинета путь фото уже разрешается через общий `app.paths`; позже стоит унифицировать загрузку настроек и держать один задокументированный способ локального запуска.
2. **Общие операции над обращениями.** Бот создаёт обращение в `app/services/issues.py`, API — в `backend/smart_city_api/services/issues.py`. Валидация, история и правила частично расходятся. Общие правила лучше вынести в `app/services`, оставив в хендлере MAX и FastAPI только адаптацию входящих данных. Новый кабинет использует существующие обращения, не переписывает эти сценарии.
3. **Разгрузить выборки списка жителя.** В `backend/smart_city_api/services/issues.py` история загружается отдельно для каждого обращения. При большой странице это N+1 запросов. Соберите историю одним запросом по ID страницы. В таблице сотрудника количество фото считается агрегатом, подробная история загружается только при открытии карточки.
4. **Объединить очереди уведомлений после стабилизации.** Старая очередь сообщений между квартирами держит транзакцию во время вызова MAX. Новая очередь кабинета фиксирует аренду задания перед сетью, затем освобождает соединение. Подход можно перенести на старую очередь и позже объединить общий механизм повторов. Две очереди сейчас сохраняют независимость работающего сценария соседей.
5. **Уточнить предметную модель ЖК.** Сейчас `House` — дом. Назначения `StaffHouse` позволяют одному сотруднику видеть несколько домов. Для нескольких управляющих компаний и комплексов с собственными названиями понадобится сущность ЖК / организации и роли; пока такой иерархии нет.
6. **Единый сценарий развёртывания.** Есть корневой Compose и отдельный `backend/compose.yaml`. Для совместной работы используйте корневой: там общая БД и том фото для бота и API. В production override включены синтетические данные — это удобно на показе, но не должно превращаться в регистрацию настоящих жильцов без проверки квартир.
7. **Хранение фото при масштабировании.** Общий том подходит для одного сервера. Если процессы переедут на разные машины, нужен общий S3-совместимый storage и выдача фото после той же проверки прав, а не локальные абсолютные пути в БД.

## Новая функциональность

Кабинет — небольшой статический frontend внутри FastAPI: `staff_web/`, маршруты `api/routes/staff.py`, сервис `services/staff.py`, авторизация `core/staff_auth.py`. Дополнительной БД, копии обращений и нового сервера авторизации нет. Сотрудники отделены от пользователей MAX. Работа с БД и сетью асинхронная; хеширование пароля и проверка файлов вынесены в поток.

Проверки и команды запуска: [staff-portal.md](staff-portal.md). Для входа нужно создать сотрудника и назначить реальные ID домов; публичной регистрации и предустановленного пароля нет.
