# Развёртывание

На сервере нужны Docker Compose v2, Nginx и действующий TLS-сертификат. Команды выполняются из корня репозитория. Подготовка переменных описана в [DOCKER.md](../DOCKER.md).

## Настройка

1. Создайте `.env.docker` из шаблона, заполните секреты и ограничьте доступ к файлу: `chmod 600 .env.docker`.
2. Адаптируйте [compose.production.yaml](../compose.production.yaml) и [nginx.conf](nginx.conf) под свой адрес: CORS, имя сервера и пути сертификатов. Эти файлы требуют настройки для нового окружения.
3. Оставьте локальный вход выключенным и `SESSION_COOKIE_SECURE=true`. `compose.local.yaml` на публичном сервере не используется.
4. Для демонстрационной регистрации включён `ONBOARDING_TEST_MODE=true`: пять домов и автоматическое принятие заявок. У API и бота значение должно совпадать. Назначьте новые дома нужному сотруднику УК по [инструкции](../README.md#сотрудник-ук). Для ручного рассмотрения выключите этот флаг. Старый `SAMPLE_DATA_ENABLED` больше не выдаёт квартиры при входе. Уже назначенные квартиры сохраняются.
5. Настройте Nginx и автоматическое продление сертификата. В настройках бота MAX укажите HTTPS-адрес мини-приложения.

Nginx направляет `/api/`, `/staff` и только точные health-маршруты `/health/live`, `/health/ready` на `127.0.0.1:8000`. Для страницы мини-приложения заданы отдельные точные правила `/health` и `/health/`: оба адреса отдают frontend без перенаправления. Подготовка считает их одной страницей, чтобы сохранённое браузером перенаправление не задерживало загрузку. Остальные страницы идут на `127.0.0.1:3000`. Frontend использует `/api/v1` на том же сайте. Порты приложений привязаны к loopback; PostgreSQL наружу не опубликована. Для входа в кабинет создайте сотрудника по [инструкции](../README.md#сотрудник-ук).

Текущее окружение: [Swagger](https://201.34.159.33/api/docs), [OpenAPI](https://201.34.159.33/api/openapi.json), [ReDoc](https://201.34.159.33/api/redoc), [liveness](https://201.34.159.33/health/live), [readiness](https://201.34.159.33/health/ready). Оба health-маршрута возвращают JSON, а не страницу frontend. Readiness возвращает 503 при недоступности БД. При переносе на другой адрес обновите `base_url` и ссылки в [DATA-API.yaml](../backend/DATA-API.yaml).

## Запуск и проверка

```sh
docker compose --env-file .env.docker -f compose.yaml -f compose.production.yaml --profile bot up -d --build
docker compose --env-file .env.docker -f compose.yaml -f compose.production.yaml --profile bot ps -a
docker compose --env-file .env.docker -f compose.yaml -f compose.production.yaml --profile bot logs --tail=100 api frontend bot
```

Проверьте `/health/live` и `/health/ready` сначала локально по `http://127.0.0.1:8000`, затем через публичный HTTPS-адрес. Откройте приложение через MAX, зарегистрируйте квартиру и создайте обращение. Вход из мини-приложения создаёт профиль жителя без предварительного `/start` в боте. Ответ 401 без сессии ожидаем. В Swagger API сотрудника проверяется через **StaffSession** после получения токена, API жителя — через **MAXLaunchData**.

## Обновление и остановка

Перед изменениями БД сохраните резервную копию PostgreSQL и фотографий. После обновления исходников повторите `up -d --build`: команда собирает образы и запускает миграции. Обычный `restart` не применяет изменения сборки и env-файлов.

После объединения веток порядок миграций: `0003` → `0004` (присутствие в мини-приложении) → `0005` (кабинет сотрудников). Если ранее была применена отдельная версия `0004_staff_portal.py`, сначала проверьте `alembic_version` и фактические таблицы: её старый номер совпадал с миграцией мини-приложения. В таком окружении не запускайте обновление вслепую и не используйте `stamp` без проверки схемы. Требуется отдельное согласование истории миграций на резервной копии БД.

```sh
docker compose --env-file .env.docker -f compose.yaml -f compose.production.yaml --profile bot down
```

Volumes сохраняются. Не добавляйте `-v`, если данные нужны. Адрес сервера, SSH-реквизиты и расположение резервных копий хранятся отдельно от документации репозитория.
